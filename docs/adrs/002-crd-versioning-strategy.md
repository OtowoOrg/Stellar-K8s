## Context

A `StellarNode` object is the declarative record of a running validator,
Horizon, or Soroban RPC deployment. It persists in etcd for the life of the
node, which for a mainnet validator is years. The operator's Rust types must be
able to read every object that was ever written by any earlier operator
release, and a cluster administrator must be able to upgrade the operator
without rewriting their manifests or losing a node.

The earlier ADR-0004 described a `v1` storage version, `v1beta1` served
versions, and a conversion webhook. None of that exists. This ADR records
what the code actually does today, states the rules contributors must follow
when changing a CRD, and sets the policy for introducing a second API version
when that becomes necessary.

### Current state (verified against `main`)

| Fact | Value | Where |
|---|---|---|
| API group | `stellar.org` | `#[kube(group = "stellar.org", …)]` on every CRD struct in `src/crd/` |
| Served version | `v1alpha1`, `served: true`, `storage: true` | `config/crd/*.yaml`, `charts/stellar-operator/templates/crd.yaml` |
| Number of CRDs | 11 manifests in `config/crd/`, plus in-crate types for tenants, chaos experiments (`chaos.stellar.org`), federation, DR policy, multi-region, secret policy | `src/crd/mod.rs` |
| Conversion strategy | Not declared, so the API server default `None` applies | No `conversion:` stanza in any manifest |
| Status subresource | Enabled for `StellarNode` (`subresources.status: {}`) | Generated by `#[kube(status = "StellarNodeStatus")]` |
| Source of truth | Rust structs. `cargo run --bin crdgen` emits the `StellarNode` manifest | `src/bin/crdgen.rs`, `make crd-gen` |
| Runtime check | `stellar-operator check-crd` fails unless `v1alpha1` is served for `stellarnodes.stellar.org` | `src/commands/check_crd.rs` |
| Finalizer | `stellarnode.stellar.org/finalizer` (versionless) | `src/controller/finalizers.rs` |

One served version, one storage version, no conversion. This is the simplest
configuration Kubernetes allows and it has been sufficient because every
schema change so far has been additive.

### How compatibility is enforced in CI today

The project already has a working, tested backward-compatibility gate. The
policy below formalises what these checks enforce rather than inventing new
process.

| Gate | What it catches | Where it runs |
|---|---|---|
| `scripts/crd_migration_lint.py --against origin/main` | A served version removed; a schema property removed; a property's declared type changed; an optional field made required. Exit 1 blocks the PR. | `quickstart-validation.yml` (with its own unit tests in `scripts/tests/`) |
| `crd-drift` job | `config/crd/stellarnode-crd.yaml` differs from what `crdgen` produces from the Rust structs. | `ci.yml` |
| `scripts/ci/extract-crd-json-schemas.py --check` | `schemas/crd/*.json` out of date with the CRD manifests. | `ci.yml` |
| kubeconform against the generated JSON schemas | Every sample and example manifest still validates against the current schema. | `yaml-schema-validation.yml` |
| `scripts/sort-manifests.py` | Non-deterministic key order in generated YAML, which would hide real diffs. | `manifest-order` job in `ci.yml` |
| `tests/compat_matrix.rs` | CRD installation, finalizer handling, and status subresource behaviour declared per supported Kubernetes minor (1.27 to 1.30). | `cargo test --test compat_matrix` |
| `make check-api-docs` | `docs/api-reference.md` stale relative to the CRD schema. | `ci.yml` |

## Decision

### Part A: Evolve `v1alpha1` in place under strict additive rules

For as long as every change can be expressed as an **additive, optional,
defaulted** change, `stellar.org/v1alpha1` remains the only served and stored
version and is modified in place. This is the Kubernetes-sanctioned approach
for alpha APIs and it is what the migration linter enforces.

A change to any struct under `src/crd/` is permitted in `v1alpha1` only if all
of the following hold:

1. **New fields are optional.** Use `Option<T>` with
   `#[serde(default, skip_serializing_if = "Option::is_none")]`, or a
   non-optional type with `#[serde(default)]` or
   `#[serde(default = "fn")]`. An object written before the field existed must
   deserialise without it. The `StellarNode` CRD module carries dozens of
   `serde(default)` attributes for exactly this reason.
2. **Existing fields are never removed and never renamed on the wire.** Rust
   renames are fine if the serialised name is preserved with
   `#[serde(rename = "…")]`. Removing a field from the schema breaks every
   stored object that has it and is rejected by the linter.
3. **Existing field types never change.** Widening `String` to an enum, or
   `i32` to `i64`, changes the OpenAPI `type` or `format` and is rejected.
   Introduce a new field and deprecate the old one instead.
4. **Optional fields never become required.** Rejected by the linter.
5. **Enum variants are only added.** Removing a variant makes stored objects
   unreadable. Adding one is safe for the operator but may break third-party
   clients that exhaustively match; call it out in the changelog.
6. **New validation is opt-in or looser.** Tightening a `pattern`, `minimum`,
   or `x-kubernetes-validations` rule can make an already-stored object fail
   validation on its next update. Tighten only through
   `StellarNodeSpec::validate()` (which reports and requeues) or through the
   admission webhook (which affects new writes only), not through the schema.
7. **Embedded upstream types preserve unknown fields.** Fields that hold
   arbitrary Kubernetes objects (affinity, tolerations, sidecar containers)
   use the `schema_utils::object_schema` and
   `array_of_objects_schema` helpers, which emit
   `x-kubernetes-preserve-unknown-fields: true`. This keeps the schema
   structural while letting users set upstream fields the operator does not
   model.
8. **The generated artefacts are regenerated in the same PR.** `make crd-gen`,
   `make generate-api-docs`, and
   `python3 scripts/ci/extract-crd-json-schemas.py`, then commit. CI enforces
   it.

**Deprecating a field within a version.** A field that is no longer the
preferred way to express something is kept on the wire and marked in Rust:

```rust
#[deprecated(since = "0.2.0", note = "Use conditions array instead.")]
pub phase: String,
```

The attribute produces compiler warnings at every use site inside the operator,
which is the mechanism that drives internal migration, while the field stays
in the schema for external readers. Three live examples:
`StellarNodeStatus.phase` (superseded by `conditions`),
`SorobanConfig.captive_core_config` (superseded by
`captive_core_structured_config`), and
`ValidatorConfig.seed_secret_ref` (superseded by `seed_secret_source`). In each
case the new field takes precedence when both are set and the old one keeps
working. The doc comment on the field must say what replaces it. Removal of a
deprecated field is a Part B event.

**Status is not part of the compatibility contract in the same way.** The
status subresource is written only by the operator, so new status fields can
be added freely. The `observed_generation` field lets clients detect a stale
status after a spec change. Status `conditions` follow the Kubernetes
`Ready` / `Progressing` / `Degraded` / `Available` convention
(`src/controller/conditions.rs`) and are the supported way to read node health.

### Part B: When and how to introduce a new API version

A second version is introduced only when a change is needed that Part A
forbids. Concretely: removing a deprecated field, changing a field's type or
semantics, restructuring nested objects, or renaming on the wire. The
Kubernetes progression is `v1alpha1` → `v1beta1` → `v1`; the project will skip
directly to `v1beta1` when the first such change is needed and will not create
`v1alpha2`.

**Rust structure.** kube-derive generates one CRD per struct, so a second
version is a second struct in a version-named module:

```text
src/crd/stellar_node/
├── mod.rs        // re-exports the version the operator reconciles
├── v1alpha1.rs   // frozen: existing StellarNodeSpec
└── v1beta1.rs    // new StellarNodeSpec with the breaking change
```

Both derive `CustomResource` with the same `group`, `kind`, `plural`, and
`shortname` and different `version`. `crdgen` combines them with
`kube::core::crd::merge_crds(vec![v1alpha1, v1beta1], "v1beta1")`, which
produces one manifest with two entries under `spec.versions` and marks the
second argument as `storage: true`. The reconciler is compiled against exactly
one version (the storage version); the API server serves the other.

**Conversion.** The API server converts between served versions using the
CRD's `conversion` strategy. The policy, in order of preference:

1. **`strategy: None`.** Valid only while the two versions' schemas are
   identical apart from additions. Use it for the release that introduces
   `v1beta1`, so that the new version exists and clients can migrate before
   any incompatible field lands.
2. **`strategy: Webhook`.** Required as soon as the shapes diverge. The
   conversion endpoint is a `ConversionReview` handler mounted on the
   existing admission webhook server (`src/webhook/`, axum over rustls, with
   cert-manager or the built-in `rcgen` issuer providing the serving
   certificate). Conversion functions are pure Rust:
   `impl From<v1alpha1::StellarNodeSpec> for v1beta1::StellarNodeSpec` and
   the reverse, with property tests asserting that `v1alpha1 → v1beta1 →
   v1alpha1` round-trips losslessly for every field the old version can
   express. Fields the old version cannot express are carried in an
   annotation so the round trip does not drop data.

There is no conversion webhook today. Building one is a prerequisite of the
first incompatible change and must ship in the same release.

**Storage version migration.** Marking `v1beta1` as `storage: true` affects
only objects written after the change. Objects already in etcd stay at
`v1alpha1` until rewritten. Before `v1alpha1` can be dropped:

1. Ship a release with both versions served, `v1beta1` as storage.
2. Run a migration: an empty patch to every `StellarNode`
   (`kubectl get stellarnodes -A -o name | xargs -n1 kubectl patch ... --type=merge -p '{}'`,
   or the `kube-storage-version-migrator`), which forces a read-convert-write.
3. Patch `status.storedVersions` on the CRD to remove `v1alpha1`. The API
   server refuses to drop a version that is still listed there, which is a
   useful guardrail.
4. Only then, in a later release, set `v1alpha1` to `served: false`, and
   later still delete it from `spec.versions`.

**Deprecation timeline.** When `v1beta1` ships, `v1alpha1` is marked in the
manifest with `deprecated: true` and a `deprecationWarning` naming the
replacement and the removal release, so every `kubectl` call against the old
version prints a warning. The old version stays served for at least
**two minor operator releases or six months, whichever is longer**, matching
the notice period the project already commits to for its REST API
(`docs/api/versioning.md`). The `check-crd` command's expected version is
bumped in the release that changes the storage version.

**Interaction with the finalizer.** The finalizer name
`stellarnode.stellar.org/finalizer` is deliberately versionless, so a version
bump does not strand objects in `Terminating`. But cleanup reads
`spec.storage.retentionPolicy` and the child-resource configuration through
the Rust struct, so an object stored at an old version must still deserialise
into the version the reconciler is compiled against. That is another reason
the storage migration in step 2 must complete before the old version is
dropped: a `StellarNode` the operator cannot read is a `StellarNode` the
operator cannot finalize, and its PVC decision cannot be honoured.

### Part C: Helm and the CRD lifecycle

The chart installs the `StellarNode` CRD as an ordinary template
(`charts/stellar-operator/templates/crd.yaml`) rather than from a `crds/`
directory. Helm skips `crds/` on upgrade; a template is upgraded. That is the
behaviour the project wants, because an operator release that adds a spec
field is useless if the CRD schema in the cluster still rejects the field.
The trade-off is that `helm uninstall` also removes the CRD and with it every
`StellarNode`. The chart's `UPGRADE_GUIDE.md` therefore instructs backing up
the CRDs before upgrade and restoring them on rollback; that procedure is
part of this decision.

## Alternatives considered

### Start at `v1` now

Rejected. Promoting to `v1` is a promise that the schema is stable for the
lifetime of the group, and the spec is still gaining a subsystem per release
wave. Declaring stability we cannot keep would be worse than staying alpha.

### Multiple served versions from day one

Rejected. Every extra version multiplies test surface and, once shapes
diverge, requires a conversion webhook, which is a highly available component
in the API server's write path. Carrying that cost before any incompatible
change exists is waste.

### Store the version in a spec field and convert in the operator

Rejected. Not idiomatic Kubernetes, invisible to `kubectl`, and it defeats
schema validation because the API server sees one schema for every "version".

### Big-bang migration (drop `v1alpha1` in the same release that adds `v1beta1`)

Rejected. Existing objects would be unreadable the moment the CRD is applied,
before the operator has a chance to migrate them, and finalized deletion would
be impossible.

## Consequences

### Positive

- Contributors have an unambiguous rule set that CI enforces mechanically;
  most PRs never need to think about versioning.
- The single-version configuration keeps the deployment simple: no conversion
  webhook, no storage migration, no per-version test matrix, until a change
  genuinely needs them.
- Deprecated fields keep working for as long as their version is served,
  which is what an operator managing years-lived validators owes its users.
- The migration path to `v1beta1` is written down before it is needed, with
  the finalizer interaction called out explicitly.

### Negative

- `v1alpha1` will accumulate deprecated fields until the first `v1beta1`
  release, and the generated schema and API reference grow with them.
- The first incompatible change is expensive: it pays for the conversion
  webhook, the storage migration tooling, and the two-version test matrix all
  at once. Maintainers should batch incompatible changes to amortise that.
- The other ten CRD manifests in `config/crd/` are currently hand-maintained
  YAML (the `crdgen` binary emits only `StellarNode`), so the drift check
  protects only one of them. Extending `crdgen` to every `CustomResource`
  struct is a prerequisite for applying Part B to those kinds, and the
  migration linter is the only mechanical guard on them today.
- The `kube-core` schema-hoisting panic noted in
  [ADR-001](001-rust-operator-architecture.md) means the drift check can be
  skipped in CI. Until it is fixed upstream or worked around, reviewers must
  confirm regeneration by hand when `src/crd/` changes.

## Compliance checklist for CRD changes

Copy into the PR description when `src/crd/` or `config/crd/` changes:

- [ ] Change is additive and optional, or this PR is an explicit Part B
      version bump approved by the maintainers.
- [ ] New fields carry `serde(default)` or are `Option` with
      `skip_serializing_if`.
- [ ] Deprecated fields are marked `#[deprecated(since, note)]` and their doc
      comment names the replacement.
- [ ] `make crd-gen`, `make generate-api-docs`,
      `python3 scripts/ci/extract-crd-json-schemas.py` run and outputs
      committed.
- [ ] `python3 scripts/crd_migration_lint.py --against origin/main` exits 0.
- [ ] A sample under `config/samples/` or `examples/` exercises the new field
      and passes kubeconform.
- [ ] `CHANGELOG.md` entry states the compatibility impact.
